# Self-Host Passwords Addendum (sub-project B.1)

**Status:** Approved 2026-06-30 after B smoke test surfaced the UX cliff. Implementation lands on branch `self-host-auth` BEFORE the merge into `self-host-server-port`.

**Motivation:** Sub-project B shipped with claim-token-only auth. Smoke testing revealed that the one-shot claim-token model breaks the natural sign-in-again UX: a user who signs out cannot sign back in without a new claim token, and members' claim tokens can only be regenerated by admin. This is fine for initial device pairing but wrong for ongoing authentication.

**Goal:** Replace the claim-token-as-credential model with a **password-based sign-in**, keeping claim tokens only for initial provisioning (bootstrap admin, admin recovery, or member invites where admin doesn't want to hand-set a password).

## Model

**Bootstrap** (unchanged): server on empty DB prints admin claim token to stdout + writes it to `data/admin-claim-token.txt`.

**Admin first-run:**
1. Admin visits `/#/claim`, enters token + device name.
2. `POST /api/auth/claim` succeeds — creates device_session, returns bearer. The `user` payload includes `hasPassword: false`.
3. Frontend detects `hasPassword: false` and routes to `/#/set-password`.
4. Admin sets a password. `POST /api/auth/set-password { newPassword }` hashes it via `Bun.password.hash()` and stores in `users.password_hash`.
5. Frontend redirects to `/#/` (Home).

**Regular sign-in (all users after initial setup):**
1. Unauthenticated device lands at `/#/sign-in`.
2. Form: label + password + device name.
3. `POST /api/auth/login { label, password, deviceLabel }` verifies via `Bun.password.verify()`, creates a device_session, returns bearer.
4. Frontend stores session, navigates to Home.

**Sign-out** (reversible now): `POST /api/auth/logout` deletes the calling device_session. localStorage cleared. Next visit → `/#/sign-in`. User signs back in with their password.

**Admin creates a member (household model):**
1. Settings → Users → Add user.
2. Modal fields: **label** + **initial password** (admin types both).
3. `POST /api/admin/users { label, password }` hashes and stores.
4. Response is `{ user }` only — no claim token needed.
5. Admin shares the label + initial password with the family member out-of-band (verbal, sticky note — this is a household).
6. Member signs in on any device via `/#/sign-in`; on first sign-in they can immediately use canvas. Optionally the frontend can auto-route them to `/#/change-password` once, but v1 keeps it manual.

**Password change (self):** Settings → Account → Change password. `POST /api/auth/change-password { currentPassword, newPassword }`. Verifies current, sets new. Optionally revokes all OTHER device_sessions (leave the current one).

**Admin resets a member's password:** Settings → Users → member row → Reset password. Admin types new password. `POST /api/admin/users/:id/reset-password { newPassword }` sets it AND revokes all device_sessions for the target user (force re-login). 409 if target is admin (admin must use change-password themselves).

**Claim tokens keep two narrow purposes:**
1. Initial admin bootstrap (unavoidable — need SOME seed credential).
2. Admin invites a member but doesn't set a password. `POST /api/admin/users { label }` (no password) still emits a claim token; the invited user redeems it and is routed to `/#/set-password` to choose their own. Useful when admin doesn't want to type a password on their family member's behalf.

Admin recovery still works via the bootstrap-recovery path: if admin loses their password AND all devices, restart the server → recovery banner emits a claim token → admin claims + goes back to `/#/set-password`.

## Schema

Single migration:

```sql
ALTER TABLE users ADD COLUMN password_hash TEXT;
```

Nullable. NULL means "user has not set a password yet." Set to argon2 hash via `Bun.password.hash(pw)`. Existing users from B's testing sessions have NULL; admin recovers via bootstrap-banner; members are reset by admin via the new endpoint.

## API surface (additions + modifications)

```
# New — sign in with password
POST   /api/auth/login              { label, password, deviceLabel }
                                    → { bearer, user: { id, label, role, hasPassword } }
                                    → 401 on wrong password or unknown label
                                    → 400 if user has no password_hash yet ({ error: 'password not set' })

# New — first-time password setup (requires bearer from claim)
POST   /api/auth/set-password       { newPassword }
                                    → 204 on success
                                    → 409 if password_hash already set (use change-password instead)

# New — password change (self, requires bearer)
POST   /api/auth/change-password    { currentPassword, newPassword }
                                    → 204 on success
                                    → 401 if currentPassword wrong
                                    Side effect: revokes ALL other device_sessions for this user, keeps current

# New — admin resets a member's password
POST   /api/admin/users/:id/reset-password  { newPassword }
                                    → 204
                                    → 409 if target is admin
                                    Side effect: revokes ALL device_sessions for the target user

# Modified — POST /api/admin/users accepts optional password
POST   /api/admin/users             { label, password? }
                                    → { user }                       (when password provided)
                                    → { user, claimToken }           (when password omitted — legacy invite path)

# Modified — /api/auth/me and /api/auth/claim responses gain hasPassword
GET    /api/auth/me                 → { user: { ..., hasPassword: boolean }, devices }
POST   /api/auth/claim              → { bearer, user: { ..., hasPassword: boolean } }
```

`user.hasPassword` is derived from `users.password_hash IS NOT NULL`. Frontend uses it to decide routing after claim.

## Frontend impact

**Routing:**
- `/#/sign-in` — default for unauthenticated users. Label + password + device name form.
- `/#/claim` — retained for token-based flows (bootstrap admin, invited members, admin recovery).
- `/#/set-password` — post-claim landing when `user.hasPassword` is false.

**New views:**
- `views/SignIn.tsx` — the new default. Two fields + device name. Auto-fills device name from UA heuristic (same as Claim.tsx). Submits via `api.authLogin`. On success: `setSession` + navigate to `/#/`.
- `views/SetPassword.tsx` — used post-claim and post-admin-reset. One password field + confirm field. Submits via `api.authSetPassword`.

**Modified views:**
- `views/Claim.tsx` — after successful redemption, if `user.hasPassword === false`, navigate to `/#/set-password`; otherwise navigate to `/#/`.
- `views/Users.tsx` — Add User modal gains optional password field; per-row Reset password action opens a modal for admin to type a new password.
- `views/Account.tsx` (or the equivalent settings tab) — gains "Change password" section (current + new + confirm).
- `main.tsx` — default unauthenticated route swings from `/#/claim` to `/#/sign-in`. `/#/claim` still routable.

**Session shape:**
`lib/session.ts` `SessionUser` gains `hasPassword: boolean`. `setSession` writes it; `getUser()` returns it.

## Password hashing

`Bun.password.hash(pw)` — argon2id by default, no additional dependency. Verifies via `Bun.password.verify(pw, hash)`. Both are async.

Minimum password length: 8 characters. Enforced client-side (better UX) AND server-side (defense).

## Out of scope

- Password strength meters, common-password lists — v1 uses length-only.
- Email-based password reset — self-hosted, no SMTP by default. Admin resets member passwords; admin recovers via bootstrap-banner.
- 2FA / passkeys / OAuth.
- Rate-limiting on `/api/auth/login`. `Bun.password.verify` timing is intrinsically constant-ish; brute-force resistance is fine for the household threat model.
- Automatic sign-out after inactivity.
- Password rotation reminders.

## Success criteria

1. Fresh boot: banner + sentinel. Admin claims token → routed to `/#/set-password`. Sets password.
2. Admin signs out → lands at `/#/sign-in`. Signs back in with password. Works.
3. Admin creates "Kid" with an initial password. Kid signs in from a different browser (private window). Works.
4. Kid changes their password from Settings → Account. Signs out, signs back in with new password. Works.
5. Admin resets Kid's password from Settings → Users. All of Kid's other device_sessions are revoked (verified by looking at Kid's Devices screen — only the current device remains if Kid was logged in when admin reset, otherwise empty).
6. Kid attempts to sign in with wrong password → 401 → friendly error inline.
7. All prior B tests still pass. Server builds + typecheck clean. Web builds clean.
