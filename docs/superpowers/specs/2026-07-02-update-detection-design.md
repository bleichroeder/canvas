# Sub-project M: Update detection + release notes — Design

**Status:** Design approved, awaiting spec review

**Context:** Canvas is a self-hosted Docker container. Users need to know when a new version is available and get it applied without thinking about Docker commands. Constraint: avoid brittle self-update mechanisms (a container replacing itself has known bootstrap problems, and the Docker socket path differs across host OSes). Solution: shift the recommended deployment to `docker-compose.yml` that includes Watchtower alongside canvas, so auto-updates are handled by a mature, portable tool. Canvas's own job is only to detect + display "what's new."

**Goal:** Ship v0.8.0 with (a) a `docker-compose.yml` at repo root that includes canvas + Watchtower as the recommended deployment, (b) a server endpoint that queries GitHub Releases for the latest published version + release notes, (c) an admin-only Settings → About card that shows current + latest + release notes, (d) a publish workflow step that creates a GitHub Release on every version tag push.

## Constraints

- **Branch:** direct commits on `self-host-server-port`.
- **Ship as:** `v0.8.0` after manual smoke passes.
- **Feature depends on the repo being public** for the GitHub API check to return data. Endpoint is built to gracefully return `null` fields + `error` message until then. Enables the code to ship pre-public-flip; useful data appears post-flip.
- **No new deps on the server.** `fetch` is Bun-native, in-memory cache is a simple object.
- **One new dep on the web side:** `marked` (or similar tiny markdown-to-HTML renderer) for rendering GitHub Release body. Release notes are the primary user-facing content; plain-text is not sufficient.
- **Endpoint is admin-only** — mounted after `requireUser` + `requireAdmin`, matching the existing telemetry admin routes.
- **Cache TTL: 6 hours.** GitHub API allows 60 unauth requests/hour per IP; ~4 checks/day is far under any limit.
- **Watchtower configuration is label-scoped.** `WATCHTOWER_LABEL_ENABLE=true` + `com.centurylinklabs.watchtower.enable=true` on the canvas container ensures Watchtower only updates canvas — never surprises the user by updating other containers on the host.
- **Watchtower poll interval: 5 minutes** (`WATCHTOWER_POLL_INTERVAL: "300"`).
- **`CANVAS_VERSION` env** is passed to the runtime stage of the Dockerfile from the `VERSION` build arg (already set for the web-build stage via `VITE_CANVAS_VERSION`; extend to runtime).
- **Release notes source:** GitHub Release body (auto-generated by `softprops/action-gh-release@v2` with `generate_release_notes: true`).

## The four moving parts

### 1. `docker-compose.yml` at repo root

New file. Users download this + run `docker-compose up -d`. Contains canvas + Watchtower with a label-scoped watch policy.

```yaml
services:
  canvas:
    image: ghcr.io/bleichroeder/canvas:latest
    container_name: canvas
    restart: unless-stopped
    ports:
      - "8787:8787"
      - "80:80"
      - "443:443"
    volumes:
      - canvas-data:/data
    # Configuration knobs — see docs/diagnostics.md for TELEMETRY_*
    # environment:
    #   TELEMETRY_ENABLED: "true"
    labels:
      # Opt this container into Watchtower's auto-update watch.
      com.centurylinklabs.watchtower.enable: "true"

  watchtower:
    image: containrrr/watchtower:latest
    container_name: canvas-watchtower
    restart: unless-stopped
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      WATCHTOWER_LABEL_ENABLE: "true"
      WATCHTOWER_POLL_INTERVAL: "300"
      WATCHTOWER_CLEANUP: "true"

volumes:
  canvas-data:
```

Ports 80/443 comments in the README explain they can be dropped for cf-quick / local deployment modes.

### 2. Server-side update detection

**New file: `server/src/lib/update-checker.ts`** — GitHub API wrapper + cache.

```typescript
export interface UpdateStatus {
  currentVersion: string;
  latestVersion: string | null;
  updateAvailable: boolean;
  publishedAt: string | null;  // ISO 8601
  releaseNotes: string | null; // markdown from GitHub Release body
  htmlUrl: string | null;
  checkedAt: string;           // ISO 8601, when cache was populated
  error: string | null;
}

// Public entrypoint: returns cached data if within TTL, else refetches.
export async function getUpdateStatus(currentVersion: string): Promise<UpdateStatus>;
```

**Cache:** in-memory `{ data, fetchedAt }`. TTL 6 hours. First request async-fetches; concurrent requests before fetch resolves share the same in-flight Promise (single-flight).

**Semver compare:** normalize by stripping leading `v`, split on `.`, compare integer-wise. `"dev"` and unparseable versions treated as older than any real version (so `updateAvailable = true` in dev if a real release exists). Function-local, no new dep.

**Failure modes:**
- GitHub 404 (private repo, no releases yet): `error: "no releases published yet"`, cache the response (avoid re-hammering).
- GitHub 5xx / network error: `error: "GitHub API unavailable"`, serve stale cache if any, otherwise fresh error response.
- GitHub 403 rate-limited: `error: "rate limited"`, serve stale cache.

**New file: `server/src/routes/updates.ts`** — mounted at `/api/admin/updates`. Single route `GET /status` returns the `UpdateStatus`. Admin-only (behind existing `requireUser` + `requireAdmin`).

**Config change** — `server/src/config.ts` adds `CANVAS_VERSION` reading `process.env.CANVAS_VERSION ?? 'dev'`.

**Server tests** (`server/src/routes/updates.test.ts`):
- Admin auth required (401 unauth, 403 non-admin, 200 admin).
- First call fetches from mocked GitHub API, populates cache.
- Second call within TTL returns cached without re-fetching (verify via mock call count).
- After TTL expires, next call refetches.
- Handles GitHub 404 → `error: "no releases published yet"`.
- Handles GitHub 5xx → serves cached if available, else error.
- Semver: `v0.7.0` < `v0.8.0`, `v0.7.0` < `v1.0.0`, `v1.0.0` > `v0.9.99`, `"dev"` < `v0.1.0`.

### 3. `Dockerfile` runtime `CANVAS_VERSION` env

Modify the runtime stage (`oven/bun:1.3-alpine`) to accept the same `VERSION` build arg and set it as `CANVAS_VERSION` for the server process:

```dockerfile
FROM oven/bun:1.3-alpine AS runtime
# ... existing setup ...
ARG VERSION=dev
ENV CANVAS_VERSION=$VERSION
# ... rest of runtime stage
```

The runtime `ARG VERSION` mirrors the web-build stage's `ARG VERSION` (both consume the same top-level build arg — already passed from publish.yml).

### 4. Publish workflow — GitHub Release step

Add one step to `.github/workflows/publish.yml`, after the existing `Build and push` step:

```yaml
- name: Create GitHub Release
  uses: softprops/action-gh-release@v2
  with:
    tag_name: ${{ github.ref_name }}
    name: canvas ${{ github.ref_name }}
    generate_release_notes: true
    draft: false
    prerelease: false
```

`generate_release_notes: true` auto-populates the body with commits since the previous tag, grouped by conventional-commit-style prefixes if used.

Permissions: the workflow already has `contents: read`. Add `contents: write` at the job level to allow release creation:

```yaml
permissions:
  contents: write   # was: read
  packages: write
```

### 5. Frontend — AboutTab.tsx "Updates" card

Extend the existing `web/src/views/settings/AboutTab.tsx`. Add a new card between the existing version display and other content.

**API method** (`web/src/api.ts`):

```typescript
adminUpdates: {
  status: () => request<UpdateStatus>('/api/admin/updates/status'),
},
```

**Card layout** (React + MUI):

- Header: "Updates"
- Row: `Current: v0.7.0`
- Row: `Latest: v0.8.0 · published Nh ago` (relative time)
- If `updateAvailable`: hint `ⓘ Watchtower will apply this update within 5 minutes.`
- If `!updateAvailable && latestVersion !== null`: line `You're on the latest version.`
- If `error`: `Update information unavailable — <error text>.` Muted.
- If `releaseNotes`: divider + "What's new" heading + rendered markdown.
- If `htmlUrl`: button "View on GitHub →" at bottom.

**Markdown rendering:** add `marked` (or similar). Small footprint (~20KB minified). Sanitize HTML output — release notes can contain arbitrary markdown, need to defend against injected `<script>`. Options: use `marked` + `DOMPurify`, or use a markdown lib that outputs safe HTML by default. Implementer picks based on bundle-size sensitivity.

**No banner outside AboutTab.** Watchtower handles the actual update; the UI is informational.

## Testing

**Server:** listed in section 2 above.

**Web:** no unit tests (following the G-L pattern of manual smoke for frontend).

**Manual smoke:**
1. `bun test` clean, `bun run typecheck` clean, `npm run build` clean, `docker build -t canvas:local .` clean.
2. Start canvas via `docker-compose up -d` (using the new compose file). Verify both `canvas` and `canvas-watchtower` containers running.
3. Log in as admin. Settings → About. Expect either:
   - "Update information unavailable" (repo still private) — expected pre-flip.
   - Current + Latest + release notes rendered — post-flip.
4. Cut a test release tag (e.g., `v0.8.1-test`). Wait 5 min. Verify Watchtower log shows update. Verify canvas came back up on new version. Verify AboutTab reflects new current version.
5. If test-release: verify GitHub Release page exists at `github.com/bleichroeder/canvas/releases`.

## Rollout

1. Cut `v0.8.0` tag.
2. Publish workflow → ghcr + GitHub Release (auto-generated notes).
3. Update David's desktop deployment: download the new `docker-compose.yml`, migrate the `canvas-data` volume in place (it survives; the compose file references it by name).
4. Verify Watchtower is running alongside canvas.
5. Manual smoke: admin sees AboutTab. If repo still private, expect "Update information unavailable" — normal.

## Out of scope

- Curated `CHANGELOG.md` (using auto-generated release notes from commit history).
- Update history / prior release archive in the UI.
- Non-admin visibility.
- Manual "trigger update now" button in the UI.
- Update banner outside AboutTab.
- Watchtower notification integrations (email / webhook).
- Server-side changelog / release-notes storage.
- Rollback UI.
